# Архитектура и пользовательский процесс

## Цель

Создать Windows-приложение для многопрофильной медицинской организации, которое открывает, заполняет, продлевает, закрывает и сопровождает электронные листки нетрудоспособности (ЭЛН) через официальный сервис МО СФР.

## Главный поток: открыть ЭЛН

1. Пользователь входит под своей учётной записью клиники.
2. Приложение загружает профиль МО и проверяет согласованность реквизитов.
3. Врач выбирает пациента/вводит идентификационные поля, указывает причину, диагноз и период.
4. Локальные проверки находят ошибки и предупреждения до отправки.
5. Интеграционный сервис запрашивает номер ЭЛН у СФР (`getNewLNNum`) либо выбирает свободный номер из ранее полученного пула (`getNewLNNumRange`). Номер нельзя генерировать случайно в клиенте.
6. Приложение строит XML строго по актуальным WSDL/XSD и правилам заполнения для конкретного состояния ЭЛН.
7. Криптографический модуль подписывает запрос от имени МО и необходимые медицинские блоки подписью врача; при необходимости добавляет подпись председателя ВК. Затем данные шифруются по действующей спецификации.
8. Запрос идёт по TLS 1.2 с ГОСТ-криптографией через провайдер, совместимый с требованиями СФР.
9. Ответ СФР проверяется по XML-подписи, расшифровывается и разбирается. Сохраняются номер, хэш, статус, код ответа, время и идентификатор запроса.
10. Состояние карточки меняется только после проверки ответа. При ошибке карточка не считается отправленной или принятой.

## Основные операции интеграции

- `getNewLNNum`: запрос одного номера ЭЛН.
- `getNewLNNumRange`: запрос пула номеров.
- `prParseFilelnlpu`: отправка/обновление сведений о листке, в том числе на открытия, продления, закрытия и соответствующие последующие статусы.
- `getLNData`: чтение актуальных данных конкретного ЭЛН по номеру и СНИЛС.
- `getLNListBySnils`: получение списка ЭЛН пациента.
- `getLNListByDate`: получение списка за дату.
- `disableLn`: отдельная операция прекращения/аннулирования, которая должна быть доступна только при наличии прав и подтверждённого бизнес-сценария.

## Архитектурные слои

### Flutter UI

Формы, списки, сценарии врача/регистратуры, локальная валидация и удобное отображение ответов. UI не должен самостоятельно реализовывать ГОСТ TLS или работать с закрытым ключом.

### Domain

Модель `ElnRecord`, статусы, периоды лечения, правила локальной проверки и контракты репозитория/API. Состояния карточки приложения отделены от официального статуса ЭЛН СФР.

### Data

Реализации локального репозитория и `SfrElnGateway`. Сейчас локальный репозиторий демонстрационный и держит записи только в RAM. Продуктивная версия должна использовать защищённую БД, транзакционное сохранение и аудит.

### Windows cryptographic bridge

Отдельный локальный процесс или нативный Windows-модуль, интегрированный с CryptoPro CSP либо другим одобренным провайдером. Предпочтительный интерфейс на первом этапе: JSON Lines в stdin/stdout с версионированными DTO и типизированными ошибками. Так проще ограничить поверхность атаки, чем открывать незащищённый локальный HTTP-сервис.

Обязанности моста: обнаружение доступных сертификатов без экспорта private key, проверка пригодности сертификата, WS-Security/XML-signature и шифрование согласно спецификации, ГОСТ TLS 1.2, проверка и расшифрование ответа, безопасное маскирование журналов.

## Безопасность и эксплуатация

- Не писать в логи полные XML, СНИЛС и медицинские сведения без строгой необходимости и правил редактирования.
- Не сохранять секреты в `settings.ini`, JSON или `SharedPreferences`.
- Не считать подключение к TCP/TLS доказательством успешного обмена: нужны корректные SOAP-конверт, криптография и валидный ответ.
- Не менять карточку на «Принят СФР» до проверки ответа и сопоставления идентификатора/хэша.
- Повтор запроса после тайм-аута должен быть идемпотентным или предваряться сверкой состояния ЭЛН.
- Продуктивная отправка должна быть выключена до завершения интеграционных тестов.


## Модуль МЧД (новый)

МЧД вынесена в отдельный раздел навигации и отдельный доменный контракт. Это не часть формы ЭЛН: жизненный цикл доверенности, формат XML и сообщения обмена относятся к сервису СЭДО и проверяются по материалам СФР.

```text
Экран МЧД
  ├── MchdRecord / MchdStatus
  ├── MchdRepository (локальные черновики + внутренний журнал)
  └── SfrMchdGateway (контракт, пока без транспорта)
          │
          ▼ после реализации
криптографический мост Windows
  ├── подпись МЧД УКЭП доверителя
  ├── ГОСТ TLS / защищённая обработка СЭДО
  └── проверка ответов и квитанций
          │
          ▼
Сервис СЭДО СФР (МЧД)
```

В локальном прототипе нельзя считать статус `registered` доказанным без подтверждения, полученного от СФР. Форма добавления существующей МЧД специально помечает введённые вручную сведения как требующие проверки.
